\begin{abstract}
This paper presents \textbf{Crypto3DStackCPU}, a validated software/HLS-ready research prototype of a cryptographic MIPS-like processor coupled to an integrated four-layer 3D-stacked-memory abstraction. The design combines a hardwired in-order pipeline with encrypted instruction fetch, encrypted data access, authenticated sealed images, executable AES-128 ISA extensions, hazard forwarding, load-use stalls, store-data forwarding, basic branch prediction/recovery, architectural performance counters, and authenticated tamper rejection. The secure image format includes a 32-word header, per-image app-key generation, key wrapping, nonce/epoch-based text block mapping, key and image tags, and post-execution reseal validation. The four logical memory layers separate encrypted text, encrypted data, key/security metadata, and tamper-sentinel information. The implementation is validated with AES known-answer tests, multi-layer memory tests, assembler negative tests, contract-driven program execution, pipeline hazard audits, memory/branch/AES benchmark workloads, and extended tamper tests. After final repository reorganization into \texttt{src/}, \texttt{programs/}, \texttt{docs/}, \texttt{paper/}, \texttt{results/}, and \texttt{hardware\_3d/}, the complete regression suite passes. The design does not claim fabricated 3D silicon, FPGA board validation, Vivado timing closure, or side-channel security; these are future work.
\end{abstract}

\section{Introduction}
% ------------------------------------------------------------

Embedded and edge systems increasingly require local computation over code and data that may be stored, transported, or loaded by an untrusted host. A conventional soft CPU normally assumes that instruction memory is already trustworthy. In contrast, a cryptographic CPU must verify and decrypt the program image before execution and must reject any tampered image before the first instruction is trusted.

Crypto3DStackCPU addresses this problem as an implementation-first research prototype. It integrates a MIPS-like instruction set, a secure image loader, an AES datapath, pipeline hazard handling, performance visibility, and a four-layer 3D-stacked-memory abstraction. The project is not only a cryptographic storage wrapper around a CPU; the same sealed image key is also available to executable AES ISA instructions, allowing a program to exercise cryptographic operations inside the CPU itself.

\textbf{Contributions.} This work contributes:
\begin{enumerate}
    \item A validated MIPS-like cryptographic CPU prototype with encrypted instruction and data regions.
    \item A four-layer 3D memory abstraction separating encrypted text, encrypted data, key/security metadata, and tamper sentinels.
    \item A sealed-image flow with key wrapping, authenticated header fields, measurement, and tamper rejection.
    \item A hardwired pipelined control path with forwarding, load-use stalls, store-data forwarding, branch recovery, and architectural counters.
    \item Executable \texttt{aesenc} and \texttt{aesdec} ISA extensions using the image-bound app key.
    \item A reproducible validation suite covering cryptographic KATs, assembler negative cases, pipeline hazards, benchmark workloads, reseal validation, and extended tamper tests.
\end{enumerate}

\textbf{Scope.} The current work is a software/HLS-ready prototype. It targets the Xilinx/AMD AC701 Artix-7 Evaluation Kit (EK-A7-AC701-G, device \texttt{xc7a200tfbg676-2}) for Vitis HLS and Vivado evaluation, but no FPGA timing closure or physical board measurement is claimed yet. Side-channel resistance and real fabricated 3D stacked-memory silicon are future work.

\section{Threat Model and Security Goals}
% ------------------------------------------------------------

\textbf{Adversary.} The adversary may inspect, copy, replace, or bit-flip the sealed image outside the trusted CPU boundary. The adversary may attempt to splice headers, modify encrypted text/data, corrupt wrapped-key fields, or provide malformed assembly programs.

\textbf{Out of scope.} The following are out of scope for the current prototype: physical probing, power/EM side-channel analysis, voltage/clock glitch fault injection, JTAG extraction of internal CPU registers, and real silicon attacks against a fabricated 3D stack.

\textbf{Goals.}
\begin{enumerate}[label=G\arabic*.,leftmargin=*]
    \item Encrypted-at-rest instruction and data regions.
    \item Authenticated image validation before trusted fetch.
    \item Failure-closed behavior on tamper detection.
    \item Contract-driven proof that the CPU executed the expected program.
    \item Post-execution reseal and reload validation.
    \item Architectural separation of text, data, key metadata, and tamper markers across four memory layers.
\end{enumerate}

\section{Cryptographic Construction}
% ------------------------------------------------------------

Each sealed image is protected by a fresh 128-bit app key $K_{app}$. A session key $K_s$ is derived from a hardware-rooted value, nonce $N$, measurement $M$, and context information:

\begin{equation}
K_s = \HKDF(H_{root}, N \parallel M, \textsf{info}).
\end{equation}

The app key is wrapped by AES:

\begin{equation}
W = \AES_{K_s}(K_{app}).
\end{equation}

Two authentication tags bind the header, wrapped key, measurement, and image contents:

\begin{equation}
T_K = \HMAC_{K_s}(\textsf{KEYT} \parallel H_{fixed} \parallel W \parallel M)[0..127],
\end{equation}

\begin{equation}
T_I = \HMAC_{K_s}(\textsf{IMGT} \parallel H_{fixed} \parallel M \parallel C_{covered})[0..127].
\end{equation}

The encrypted text region is block permuted. For text block $b$ among $L$ blocks:

\begin{equation}
\pi(b)=((m b + a) \bmod L)+start,
\end{equation}

where $\gcdop(m,L)=1$ ensures invertibility.

\section{Algorithms}
% ------------------------------------------------------------

\begin{algorithm}[!t]
\caption{Seal Image}
\label{alg:seal}
\footnotesize
\begin{algorithmic}[1]
\Require Plain text words, plain data words, epoch, policy
\State Generate fresh app key $K_{app}$.
\State Create fixed header fields and region descriptors.
\State Generate nonce $N$ and block mapping $\pi$.
\State Encrypt text blocks using $\AES_{K_{app}}$ and place by $\pi$.
\State Encrypt data blocks using $\AES_{K_{app}}$.
\State Compute measurement $M$ over fixed fields and covered ciphertext.
\State Derive session key $K_s$ using HKDF.
\State Compute wrapped key $W=\AES_{K_s}(K_{app})$.
\State Scatter/check hidden key metadata through the layer abstraction.
\State Compute $T_K$ and $T_I$.
\State Emit sealed image.
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[!t]
\caption{Validate Image Before Fetch}
\label{alg:validate}
\footnotesize
\begin{algorithmic}[1]
\State Read header fields.
\If{magic/version/policy/regions are invalid} \State reject \EndIf
\State Recompute mapping $\pi$ and measurement $M'$.
\If{$M' \ne M$} \State reject \EndIf
\State Derive $K_s$.
\State Verify wrapped-key consistency.
\State Verify key tag $T_K$.
\State Verify image tag $T_I$.
\If{all checks pass}
    \State unwrap app key and unlock fetch/decrypt path.
\Else
    \State lock CPU and refuse execution.
\EndIf
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[!t]
\caption{Pipeline Hazard Control}
\label{alg:hazard}
\footnotesize
\begin{algorithmic}[1]
\Require Current decode instruction and later pipeline registers
\State Detect source registers of decode instruction.
\State Compare sources with destinations in execute/memory/writeback.
\If{value available from memory-side pipeline stage}
    \State forward from memory-side result.
\ElsIf{value available from writeback stage}
    \State forward from writeback result.
\ElsIf{load-use dependency cannot be forwarded yet}
    \State insert stall and increment load-use stall counter.
\EndIf
\If{store instruction needs just-produced store data}
    \State forward store data and increment store-data-forward counter.
\EndIf
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[!t]
\caption{Branch Prediction and Recovery}
\label{alg:branch}
\footnotesize
\begin{algorithmic}[1]
\State Predict next block using the static frontend rule.
\State Execute branch/jump and resolve actual next block.
\If{predicted block differs from resolved block}
    \State flush fetch/decrypt/decode registers.
    \State restart fetch at resolved block.
    \State increment branch-mispredict counter.
\Else
    \State continue without recovery.
\EndIf
\end{algorithmic}
\end{algorithm}

\section{Pipeline and Control Unit}
% ------------------------------------------------------------

The CPU is a hardwired in-order pipeline with a dedicated decrypt stage between fetch and decode. The pipeline stages are:

\begin{center}
\texttt{Fetch $\rightarrow$ Decrypt $\rightarrow$ Decode $\rightarrow$ Execute $\rightarrow$ Memory $\rightarrow$ Writeback}
\end{center}

Unlike a textbook unencrypted MIPS pipeline, Crypto3DStackCPU cannot decode directly from memory. The Fetch stage reads encrypted blocks, the Decrypt stage uses the validated app key, and only then can Decode interpret the instruction word.

The control unit is hardwired rather than microprogrammed. This choice keeps the secure fetch/decrypt/execute path deterministic and easier to validate.

\section{Hazards, Forwarding, and Branch Handling}
% ------------------------------------------------------------

The design implements basic but functional in-order hazard support. The final regression suite validates two load-use stalls and one store-data forwarding event in the pipeline hazard benchmark. Forwarding from later stages reduces unnecessary stalls.

\textbf{Load-use hazard.} If an instruction consumes the result of an immediately preceding load before the value is available, the decode stage inserts a stall.

\textbf{Forwarding.} ALU results can be forwarded from memory-side or writeback-side pipeline registers. The counters \texttt{forward\_mem} and \texttt{forward\_wb} expose those events.

\textbf{Store-data forwarding.} If a store needs a value produced by a prior instruction, the store data can be forwarded instead of reading stale register-file data.

\textbf{Branch recovery.} Branches and jumps are resolved deterministically. If the predicted block is not the resolved block, the frontend is flushed and fetch restarts at the correct block. The counters \texttt{branch\_predictions} and \texttt{branch\_mispredicts} expose this behavior.

\section{Memory Hierarchy}
% ------------------------------------------------------------

The memory hierarchy is security-oriented:

\begin{enumerate}
    \item Pipeline registers and AES co-processor state.
    \item Instruction/data cache visibility counters and access buffers.
    \item Four-layer 3D-stacked-memory abstraction.
    \item Sealed host image file.
\end{enumerate}

The design does not implement a conventional L1/L2/L3 cache hierarchy. Instead, it emphasizes encrypted-at-rest memory and validated access through the CPU boundary. Data loads/stores to sealed data memory follow a secure decrypt/modify/encrypt path.

\section{Performance Counters and Amdahl-Style Interpretation}
% ------------------------------------------------------------

The testbench reports counters over a fixed validation window of 2000 cycles. CPI is reported as:

\begin{equation}
\text{CPI}_{window}=\frac{\text{validation window cycles}}{\text{retired instructions}}.
\end{equation}

This should not be interpreted as final FPGA performance. It is an architectural visibility metric for regression comparison.

If a fraction $f$ of the validation time is dominated by a component such as AES decrypt or memory handling, and that component is accelerated by factor $S$, the classical Amdahl bound is:

\begin{equation}
\text{Speedup}=\frac{1}{(1-f)+\frac{f}{S}}.
\end{equation}

This provides a structured way to discuss future Vitis/Vivado optimization: accelerating only the AES datapath or only the memory path cannot improve the whole system beyond the non-accelerated fraction.

    \item fabrication, PDK, GDSII, and foundry checklists;
    \item paper appendix material describing the real 3D memory scope.
\end{itemize}

These files do not mean that a chip was fabricated. They provide a structured path toward real hardware integration.

% ------------------------------------------------------------
\section{Limitations}
% ------------------------------------------------------------

\begin{itemize}
    \item The current implementation is not FPGA board validated yet.
    \item Vivado timing closure and resource reports are not yet available.
    \item AES is functionally validated but not side-channel hardened.
    \item The 3D stack is an abstraction/model and hardware-readiness package, not fabricated silicon.
    \item The CPU is in-order and does not implement out-of-order execution, Tomasulo scheduling, superscalar issue, or VLIW dispatch.
    \item CPI counters are fixed-window validation metrics, not final optimized performance numbers.
\end{itemize}

\section{Future Work}
% ------------------------------------------------------------

Future work includes:

\begin{enumerate}
    \item Vitis HLS CSIM and synthesis with the reorganized \texttt{src/} paths.
    \item Vivado IP integration and validation on the AC701 Artix-7 Evaluation Kit (\texttt{xc7a200tfbg676-2}).
    \item Timing, area, and resource reports.
    \item Side-channel hardening with bitsliced/masked AES and physical leakage measurements.
    \item Fault-injection detection and redundant AES checks.
    \item Optional dynamic branch predictor, scoreboard, or deeper memory hierarchy.
    \item Multicore/NoC extension and secure 3D shared-memory experiments.
    \item ASIC-ready RTL, PDK collaboration, GDSII signoff, and real 3D stacked-memory fabrication if foundry access becomes available.
\end{enumerate}

% ------------------------------------------------------------
\section{Conclusion}
% ------------------------------------------------------------

Crypto3DStackCPU demonstrates that a compact MIPS-like CPU can be combined with a secure image format, AES-backed instruction and data confidentiality, authenticated tamper rejection, a four-layer 3D memory abstraction, executable AES ISA extensions, practical pipeline hazard handling, branch recovery, and architectural benchmarking. The final organized repository passes the full regression suite, including cryptographic KATs, multi-layer memory tests, assembler negative tests, demo audits, hazard audits, benchmark workloads, and extended tamper tests. The next milestone is hardware validation through Vitis HLS, Vivado, and Artix-7.
